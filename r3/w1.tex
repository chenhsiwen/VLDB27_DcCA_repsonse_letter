\paragraph{R3-W1 (Techniques reduce to a common pipeline; apparent contradiction; prototype uses third-party libraries such as FAISS).}

\begin{itemize}[leftmargin=1.2em, itemsep=1pt, topsep=2pt]
\item \textit{W1: ``The proposed techniques \dots reduce to a common pipeline: embedding, index construction, nearest-neighbour search, and utility-based subset selection \dots the authors simultaneously discuss that these elements can be handled as separate stages within existing systems. This contradiction weakens the case \dots the experiment in DcCA also treated the criticized stages independently with third-party libraries, e.g., using FAISS \dots''}
\end{itemize}
\smallskip

\noindent\textbf{Response.}
We appreciate this observation and clarify the apparent contradiction, which comes from the paper serving two distinct goals: (1) articulating a \emph{vision} for future data management systems, and (2) building a proof-of-concept prototype with today's systems. There is no contradiction between the two.

\textbf{The vision.} The central thesis is that counterfactual querying should become a \emph{first-class data management primitive}. Existing systems expose vector search, filtering, reranking, and subset selection as independent operators. We argue that the opposite-outcome predicate, feasibility constraints, intervention cost $\omega$, and set objective $\Omega$ should instead be part of the declarative query semantics, so a database optimizer can reason about them jointly during query optimization, index construction, and execution planning.

\textbf{The prototype.} Because current systems do not yet support this abstraction, our prototype is intentionally built from existing components---FAISS for candidate retrieval, plus feasibility validation and set optimization. FAISS is used \emph{only} as a proposal mechanism for generating candidate counterfactuals; it does not implement the semantics we advocate. The remaining components approximate the desired semantics outside the retrieval engine precisely because current systems provide no way to optimize them jointly.

Our point is therefore not a criticism of FAISS or other mature retrieval components; it is that current database systems can only treat these components as separate stages, and that staging is what is insufficient. The prototype shows counterfactual querying is practical with today's infrastructure, while the vision identifies the next research challenge: elevating counterfactual querying from an application-level workflow to a native database abstraction in which feasibility, intervention cost, and set-level objectives are optimized together. Our new quality study (Table~\ref{tab:quality}) illustrates why the ``utility-based subset selection'' stage is not interchangeable with generic top-$k$: top-$k$ is optimal for none of the set-level objectives. We revised Section~5.1 to explicitly separate the current proof-of-concept from the long-term vision and to clarify FAISS's role as the proposal mechanism only.
